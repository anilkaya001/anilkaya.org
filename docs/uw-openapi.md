## Refreshing it

Open item: the refresh below has not been done. The builder of P1-38 had no vendor access (the documentation host answers 403 from the sandbox), so `docs/uw-openapi.yaml` is still the 2026-08-30 copy and the row is not fully closed until steps 1 to 6 are run by someone who can reach the document; the one `specSha256` move in step 5 is its closing commit.

5. Run `python3 tests/gen-dossier-fixtures.py`. It builds the dossier fixtures from the spec's types and the manifest's names and exits 1 where the two disagree: a name the fixtures emit that the wire did not carry, a rename the spec now documents, an unseen name the spec no longer lists. 6. Run `npm run test:flows-probe` and `npm run test:flows-dossier` from `tests/`.

## The catalog and the refresh workflow

`node scripts/gen-feed-catalog.mjs` turns this file into `shared/flows-feed-catalog.js`, the committed catalog of every operation and socket channel the feed's document describes (218 operations and 30 channels today), and `shared/flows-feed-client.js` builds requests and reads answers through it; `--check` exits 1 when the catalog is not what this file generates, and `--coverage` prints which operations and channels production reads. A parameter the document puts in a header or a cookie is recorded as the document gives it. The client builds no request for such an operation (the reason is `place`), and `--coverage` lists those operations under `elsewhere`. There are none today.

The client spells each path parameter as one segment and refuses `.` and `..` (reason `segment`), because an address resolves them away. The registry's own `pathFor` in `shared/flows-vendor-ops.js` does not refuse them yet: `pathFor("greeks", { ticker: ".." })` builds `/api/stock/../greeks`, which `vendorUrl` turns into `/api/greeks`. `TICKER_RE`, which the Worker's ticker routes check first, starts with a letter, so neither value passes it there. The other call sites (243 in all) have not been audited for this. The fix is a change of its own, because this slice leaves the registry as it is: it would refuse both by name, add a planted build, and pass the hostile values through `vendorUrl` in `tests/flows-probe-contract.mjs`.

The catalog lists what exists, not what the site may read. What may not be read is written down beside the client, in two tables, and the client enforces both:

- `FEED_HELD`, the operations that are never asked for: the people lookup of the prediction markets ("The site does not look people up.", `docs/packages/WP5-cross-asset-macro.md` 2.3) and the feed's one write, the creation of an alert configuration ("The site reads the feed and writes nothing to it.", `docs/packages/WP6-event-risk.md` 3). The client refuses to build a request for either and to read an answer of either, with the reason `held`; no option lifts a hold, and the client builds reads only. `--coverage` prints the two under `held`, apart from the operations nobody reads yet.
- `FEED_HELD_FIELDS`, the fields WP5 2.3 says are not read, as rules by operation family: wallet addresses and names, leaders' names, the feed's seasonal averages, its unexplained scores, and the volume of spot bars. The reader leaves them out of every answer, at any depth, and names them under `withheld`. Two entries go past the house's table as written: `counterparty_address` is held although WP5 does not list it, because it is a wallet address too; and `user_address` is withheld although the nightly's odds leg reads it by hand for three holders, so moving that leg onto the client needs a reviewed exception first. A socket frame is read with no hold, because no channel documents a wallet or a leader's name today; the suite fails when a refreshed document puts one on a channel or on an operation outside those families.

What the packages decide leaf by leaf is not in the client, and a consumer that reads through it still has to honour its own package's table: a figure whose unit the document does not state is not printed (WP3's list for the volatility operations, the unit test for the movers' `change_percent`), and text meant for a reader or a model (`description`, `question`, a headline) is handed over as it came and still goes through the dossier's sanitiser.

How an answer is wrapped is read off the schema for 69 operations and off the document's own example for 109; for the other 20 the wrapper `data` is assumed. The committed observation of the wire (`scripts/flows-probe-shapes.json`) settles the wrapper for the 67 operations it recorded. `FEED_WIRE`, beside the client, lists what the wire sent for each of them: 64 confirm the document, short volume came under `si`, and two came as bare lists. The reader takes an answer that has no key around it only where there is evidence for that form. An assumed row qualifies when the object holds a field the schema documents. An answer the schema leaves open qualifies only when the document's example shows the answer itself, and the object holds one of the keys that example shows; two operations are like this, and the catalog records their keys as `exampleKeys`. An operation in that observation never qualifies, whether the wire confirmed the document or not. Anything else without its key is `unshaped`, an error object included, and the suite holds that for every operation that answers JSON. The result says which form was read (`form`). A field is marked `numeric` when the schema says a string carries a number or, where the schema is silent, when the document's example for it is a decimal written as text: 23 marks rest on the example alone (`forecast` of the economic calendar is one), and in 11 fields the declared kind was set aside because the example contradicts it. An example is one row, so such a field can be free text on another row; the reader then fails that answer by name (`type:<field>`) and never guesses. Folding the first live walk's `type:` failures, wrappers and forms into `FEED_WIRE` is therefore a step of the slice that first calls the feed through the client, before anything is built on those answers.

Step 1 above now has a tool: the workflow `feed-spec-refresh`, started by hand, has `scripts/feed-spec-refresh.mjs` download the document, by default from the documentation page this file links to and otherwise from the address typed into the run, and `with_key` lets it ask once more with the feed key when the feed's own origin refuses an anonymous request. The feed's origin is the one production calls (`VENDOR_BASE_DEFAULT`), whatever a document says. The run refuses anything that is not a whole document of at least 200 paths whose servers are all the feed's, reads at most 20 MiB and for at most 60 seconds, writes the `uw-spec-diff` comparison to the run's summary, and pushes the new file alone to the branch `claude/feed-spec-refresh`; it never touches `main` and opens no pull request. Once the document has been read and compared, the comparison is written to the summary before any later refusal, so a refused run still says what moved. Such a refusal says why on its `refused` line. When it says the catalog cannot be built, the document uses something the generator does not read, such as a parameter placed outside the path, the query, a header or a cookie. The document is then not written. The remedy is a change to `scripts/gen-feed-catalog.mjs` and `tests/gen-feed-catalog-oracle.py`, in a pull request of its own, after which the run is started again. It has only been run against a local stand-in server (`tests/flows-feed-spec-refresh.mjs`), so whether the documentation page links to the document, and whether that needs the key, is not known until someone runs it.

After it has pushed, the rest is by hand, on a branch of your own cut from `claude/feed-spec-refresh`. Do not commit the follow-up to `claude/feed-spec-refresh` itself: a later run replaces the workflow's own single commit there, fast-forwards a branch its checkout already holds, and otherwise stops with nothing pushed and says the branch holds other work. On your branch, record the address, the date, `info.version` and the sha256 in the table above; run `node scripts/gen-feed-catalog.mjs`, `node tests/gen-feed-fixtures.mjs` and `python3 tests/gen-feed-catalog-oracle.py` (it needs PyYAML) and read their diffs; then steps 4 to 6 above and `node flows-feed-catalog.mjs` from `tests/`, whose pinned lists (the names production reads that the document lacks, the wrappers the wire uses, the registry entries the document does not describe, the fields each hold covers) say what the new document changed. A new operation or field that belongs under a hold is added to the tables by hand; nothing infers it.

## What may and may not be committed

No vendor value belongs in a committed file, an Actions log, an issue or an artifact. The probe prints names, JSON types, nullability and counts of documented enum tokens, and `scripts/flows-probe-shapes.json` holds those and nothing else. Fixtures are synthetic: a fixture's `source` field may say which generator wrote it and may not say that its rows are verbatim vendor rows or came from a live probe. `tests/flows-probe-contract.mjs` fails on those words in any new fixture and pins the four older fixtures that still carry them until they are regenerated.
